# Schedule Sync Data Integrity & Reliability Repair v1

Baseline: `main` at `58f052997d7e086d7630e70f93f4e92e07f3705a`.
Scope: input admission, safe persistence and historical inspection in this repository only. Creative OS is unchanged. No real browser schedule was accessed, repaired, normalized or deleted during this work.

## Actual root causes

1. **PC feed range admission:** the parser checked `isNaN`, not calendar/hour/minute ranges. Numbers such as 30 hours, 75 minutes and February 30 could reach stored ISO strings. Explicit AM/PM hours outside 1–12 were also accepted. Bare-hour meridiem inference could incorrectly alter explicit 24-hour midnight input.
2. **PC feed tokenization:** a portion of a time range could be recognized as a numeric date. For example, `00-17` inside `08:00-17:00` could split the line and change month/day context. The parser could also interpret a bare range such as `8-5` as a numeric date. Invalid date context could leak into later lines, an explicit numeric year was ignored, and a missing day defaulted to today instead of rejecting an incomplete input.
3. **Manual Add/Edit:** `new Date(end) <= new Date(start)` does not reject `Invalid Date` because comparisons with NaN are false; JavaScript can also roll impossible dates forward. Edit mutated the live shift before storage succeeded, so failure could leave memory changed.
4. **QR/hash import:** rows were decoded without admission validation; unrecognized rows could be dropped and an empty/invalid result could clear the current schedule. QR export omitted the end date, and import assigned the start date to the end, losing overnight meaning.
5. **Storage:** load/storage-event paths accepted arrays without inspecting their rows. Persistence swallowed errors, did not guard staged records, and could leave the two keys inconsistent after a partial write. The two copies could already differ without being disclosed.

**Could the known real malformed record have come from the old code?** Yes, plausibly. A focused synthetic reproduction runs the old baseline parser and confirms that inputs containing `30:00`, `08:75` and February 30 result in persisted malformed records. This proves a creation path for this defect class, not the provenance of a specific real record. The real record's raw values/history were not provided or inspected here; its exact origin cannot be established from this audit.

## Paths fixed

- `shift-integrity.js`: shared, non-mutating calendar/ISO/hour/minute/seconds/interval checks, record/identity checks, historical issue inspection and read-only dual-key inspection. Valid local times compare as calendar values, independent of the host's Date rollover behavior. Explicit-offset endpoints are supported; mixed local/offset endpoints are rejected. Calendar years are 1900–9999, matching the exporter's lower bound. Source-timezone/DST validation remains the exporter's additional responsibility; no source timezone is invented here.
- `index.html` → `processTranscript`: validate raw ranges before AM/PM conversion and validate converted hours before construction; require a date; honor explicit years; avoid recognizing times as dates; do not let a rejected date poison following rows. Stage and validate new records before persistence. Invalid chunks are listed and the transcript remains available; only valid chunks may be added. A backwards clock range must explicitly say night/overnight/graveyard before constructing its actual following end date. Ordinary bare-hour conventions remain for valid inputs; explicit 24-hour values are not passed through those conventions.
- `index.html` → `saveNewShift` / `saveEditedShift`: validate the complete staged candidate through the persistence boundary before publishing it. Edit uses a copy and preserves the original ID. Invalid input and storage failure do not update the live record. Explicit next-day end dates are required for manual overnight entries.
- `index.html` → `processSyncHash`: inspect the entire incoming batch, identify bad rows, and reject the entire replacement if any fail. Empty imports do not clear existing data. Valid legacy same-day payloads remain supported. New QR export appends an eighth end-date field; current import validates that explicit date. Legacy reversed overnight payloads are rejected because their lost date cannot safely be guessed. The Creative OS JSON schema is unchanged.
- `index.html` → `persist(next)`: validate new/changed records, reject newly conflicting IDs, serialize candidates, write both existing keys, and publish state only after both writes succeed. Untouched historical objects may be retained without repair when a legitimate new change is saved. Detect out-of-date storage copies before writing. Attempt to restore original key bytes after a partial write; if restoration fails, block further saves and disclose that failure. localStorage has no atomic multi-key transaction, so crash-level atomicity is not claimed.
- `index.html` → `loadStoredSchedule`, storage listener, `refreshIntegrity`, `scheduleForDisplay`: no load-time writes or migration. Preserve both existing keys and their contents. Keep the original primary-key precedence, disclose malformed JSON/non-array copies or differing copies, and block saves while a storage conflict needs review. Read-only Inspect buttons identify preserved bad records, including records in a differing secondary copy. Invalid records are withheld from normal schedule cards so rendering/date rollover cannot make them appear valid; a persistent warning says the schedule may be incomplete. They remain in the source array and storage, and the unchanged strict Creative OS exporter still rejects them.
- `creative-os-problem.js`: accept a historical read-only presentation option; immediately show raw title, ID, details/room, category, start/end and legacy fields, with no editor dispatch or save action. The default export problem-shift behavior remains available. Existing normal-editor entry is guarded against unparseable historical records; parseable reversed intervals can be opened for an explicit user edit, but cannot be saved until valid.

No Slack/Apple Calendar ingestion or write behavior was added or changed. No automatic synchronization, source-data correction, deletion, browser scraping or storage clearing was added. Both `vet_shifts_backup` and `schedule_sync_shifts` are retained. Explicit user actions can still save an intended valid update or delete through the existing Delete UI; merely loading/inspecting/dismissing does not write either key.

QR compatibility: refresh both sending and receiving app instances after this change is deployed. An old cached receiver ignores the appended end date and cannot safely handle overnight transfers; the updated receiver rejects legacy overnight payloads instead of guessing their missing date.

**52 passed**: 46 integrity/admission/storage checks and 6 affected problem-shift UX checks. Repeat runs are the same cases, not additional unique tests. No broad or unrelated historical suite was run. The old-code execution is a narrow synthetic reproduction inside the new integrity test, not a historical-suite rerun.

Checks cover invalid hours/minutes/impossible dates; normal/leap/overnight values; malformed dictation with no writes; normal/mixed/overnight dictation; real Add/Edit handlers and unchanged memory on invalid edits; all-or-nothing QR validation; explicit overnight QR round trip and rejection when an end date is missing; exact load-time key-byte preservation; read-only historical inspection/dismissal; malformed rows remaining stored while valid rows remain logically unchanged; conflicting/corrupt keys; partial-write rollback; stale concurrent copies; and storage-event detection. Tests execute the actual inline handlers with synthetic data and mocked DOM/storage. They do not manipulate a real browser schedule or establish live personal-data accuracy.
